    2. A few orphan nodes (System "Redis", System "Notion", two Terms) — extracted as entities but the LLM didn't emit an accompanying fact for them, and entities are written unconditionally while edges require a validated fact, so they end up disconnected
  - **fixed (1) — lightweight similarity dedup at write time**: `graph/search.find_similar_uid()` — before minting a new Decision/Term uid, check vector distance against existing same-label nodes; reuse the existing uid if distance ≤ 0.1. Calibrated against real embeddings first: FalkorDB's vector score is a *distance* (0 = identical) not similarity — a real near-duplicate pair scored ~0.04, an unrelated pair ~0.80, so 0.1 has wide margin both ways. Deliberately narrower than full Tier-3 (plan.md §5): only ever reuses an existing uid for what looks like the same entity, never creates a new inferred edge on similarity alone. Verified directly: a controlled near-duplicate pair correctly merged, a controlled unrelated pair correctly did not

  - **found and fixed a second real bug, from the user's own testing**: "delete connection" in the UI appeared to do nothing. - [x] **Block 10 follow-up 2** — fixed the orphan-entity gap for real (user pushed back: "who decided it should work like this, can't extraction just be better?")
  - root cause: entity extraction (`terms`/`decisions`/`systems`) and fact extraction (`facts`) were two independent lists in the schema — nothing required an entity to appear in any fact, so the LLM could (and did) name a System/Term with no connecting relationship, and the write path created the node unconditionally regardless
  - fixed structurally, not just by asking nicely: `_write_extraction` now computes which (kind, name) pairs actually appear as a fact's subject/object, and drops any extracted Term/Decision/System that isn't referenced by at least one fact, logging what got dropped and why — an orphan can no longer reach the graph even if the LLM produces one
  - also strengthened `_WORK_MANAGEMENT_ADDENDUM` (the extraction prompt) to state this rule outright, so the LLM stops wasting extractions on things it won't connect, rather than relying on the drop-filter as the only defense
  - re-tested with two near-duplicate tickets (one also mentioning Notion for design tracking): 8 entities extracted, 6 facts written, **zero dropped** — the prompt fix alone was enough this run, the structural filter is the backstop for when it isn't
